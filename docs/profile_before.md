# Профіль до змін (Lab 8, M1)

Машина: i7-6700HQ (4 ядра / 8 потоків), Windows 10, Python 3.14.2. Корпус: 20 книжок Project
Gutenberg, 1 374 895 токенів, індекс на 57 901 термінів. Усі числа нижче виміряно до будь-яких
правок. cProfile сильно сповільнює код із мільйонами дрібних викликів, тому довіряю порядку
функцій, а не абсолютним секундам.

## `findex search`

Команда: `uv run python -m cProfile -o docs/search.prof scripts/profile_search.py index.bin data/raw "war OR money OR gold" 10`
(10 пошуків, k=10, кожен результат отримує сніпет; індекс вантажиться один раз).

| # | Місце | Власний час | Разом | Викликів |
|---|---|---|---|---|
| 1 | `tokens.token_spans` | 27.1 с | 35.8 с | 10 422 346 |
| 2 | `snippets._best_center` | 5.7 с | 5.7 с | 100 |
| 3 | `snippets._find_matches` | 3.2 с | 39.0 с | 100 |

`make_snippet` разом дає 45.5 с із 47.2 с (96%). Сам скорер BM25 у топ-15 не потрапив. Завантаження
індексу (`load_pickle`) коштує ~1 с, один раз на процес.

Гіпотези (записані до правок):

1. `token_spans`. Це час у Python, а не лише в regex: на одній книжці (328 тис. токенів) `findall`
   (нативне сканування) займає 330 мс, а повний `token_spans` 543 мс, тобто 61% нативного коду й
   39% накладних витрат Python (генератор, `group`, `lower`, `start`, `end`). Але головна проблема
   алгоритмічна: кожен запит заново токенізує десять цілих книжок (~104 тис. токенів на виклик).
   Гіпотеза: токени кожної книжки треба порахувати один раз і зберегти як масиви NumPy (id терміна,
   початок, кінець), а збіги шукати як `np.isin` по цих масивах.
2. `_best_center`. Чистий Python, O(m²): для кожного збігу будується множина по всіх збігах.
   Гіпотеза: це замінюється ковзним вікном через `np.searchsorted` (O(m log m)) або двома
   вказівниками.
3. `_find_matches`. Python-вираз із перевіркою `t in wanted` для кожного токена книжки. Після
   правки з пункту 1 цей цикл зникає.

Висновок до M2: скорер не є вузьким місцем, тому NumPy-версія BM25 майже не змінить час
пошуку в цілому. Справжній виграш дасть переробка сніпетів.

## `findex index`

Команда: `uv run python -m cProfile -o docs/index.prof -m findex index data/raw --out tmp_index.bin --executor serial`
(9.5 с за годинником, 10.7 с під профайлером).

| # | Місце | Власний час | Разом | Викликів |
|---|---|---|---|---|
| 1 | `tokens.token_spans` + обгортка `tokenize` | 4.1 с + 0.7 с | 6.6 с | 1 374 895 |
| 2 | `re.Match.start()` / `.end()` у `tokenize` | 0.39 с + 0.35 с | 0.74 с | по 1 374 895 |
| 3 | `pickle.dump` | 0.24 с | 0.87 с | 1 |

`threading.wait` (0.76 с власного часу) у таблиці не враховую: це головний потік чекає на
потік смуги прогресу, а не робота.

Гіпотези:

1. Токенізація: час у Python, а не в regex. Генератор у генераторі (`tokenize` викликає
   `token_spans`), і кожен токен проходить через `yield` двічі.
2. `start()` і `end()` викликаються для кожного токена, але `tokenize` їх відкидає. Гіпотеза:
   версія `tokenize` без позицій (`findall` + `str.lower`) прибере це без зміни результату.
3. `pickle.dump` та 115 тис. викликів `dataclasses.fields` показують ціну збереження мільйонів
   дрібних об'єктів `Posting`. Зберігання постінгів як масивів NumPy має це зменшити.
